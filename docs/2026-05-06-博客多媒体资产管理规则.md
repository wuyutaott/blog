# 博客多媒体资产管理规则

> 创建日期：2026-05-06
> 范围：本博客项目所有图片 / 视频 / GIF / 音频资产
> 性质：项目级规则文档

## 占位符约定

文档中出现的 `${DOMAIN}`、`${VPS_IP}`、`${VPS_HOST}` 等占位符对应运维敏感值，真实值存放于项目根的 `.env` 文件（已加入 `.gitignore`，不进版本库）。

执行下文中含占位符的命令前，先在 shell 中加载：

```bash
source .env
```

加载后所有 `${DOMAIN}`、`${VPS_HOST}`、`${VPS_IP}` 在命令里会被自动替换为真实值。

> 代码示例（Python / JS 等）中的 `${DOMAIN}` 是同一约定的延伸：
> 真实运行时请改写为从环境变量读取，例如 `os.environ["DOMAIN"]`。

## 0. 这份文档的由来

调研了三个开源博客项目（Weekly / blog / tw93.github.io）的图片视频管理方式，对比利弊后，决定**先不建多媒体管理平台**，只用一套约定规则跑。

### 为什么不建平台

不是因为"做不起"。AI 时代写代码本身没什么代价。**真正的问题是平台引入的运行时风险和架构复杂度**：

| 思路 | 引入的复杂度 / 风险 | 适用场景 |
|---|---|---|
| 建带 UI 的 DAM 平台 | 有状态系统、自维护数据库、单点故障、半成品 DAM 比没有 DAM 更糟（误删 / 损坏不可恢复） | 多人协作 / 资产 > 10000 |
| 写 manifest 文件做映射 | 一个文本文件 + 一个构建插件，零运行时，可 git 版本化 | 频繁迁移 / 跨项目复用 |
| **纯规则约定（本方案）** | **零代码零状态，所有约束在大脑+文档里** | **单人博客 / 资产 < 1000** |
| 直接硬编码各种 URL | 零结构，但迁移时要改一堆文章 | 不在乎将来迁移 |

对单人博客 + 资产规模 < 1000 来说，平台带来的"出错面"远大于它解决的问题。等真的撑不住了再升级到 manifest，再不行才考虑平台。

### 核心心法

> **状态越多，出错面越大。先用最少状态的方案跑。**
>
> - 规则：零状态，约束写在大脑和文档里
> - 脚本/CLI：零状态，每次运行重置
> - manifest 文件：弱状态，但纯文本可版本化
> - 数据库 / 服务：强状态，引入持续运行风险
>
> 默认从最左边开始。每一次"加状态"都要有明确的理由。

## 1. URL 形式（最重要的一条）

**所有图片视频的 URL 必须以 `cdn.${DOMAIN}` 开头。**

```
✅ https://cdn.${DOMAIN}/2026/05/iceland-aurora.jpg
❌ https://${VPS_IP}/images/aurora.jpg          （直连 IP，泄露源站）
❌ https://my-account.r2.cloudflarestorage.com/... （锁定厂商，迁移要改文章）
❌ https://cdn.fliggy.com/upic/xxx.mp4              （白嚼别人 CDN，不可控）
```

### 为什么必须走自有子域

- 换后端只改 DNS（CNAME），URL 永远不变，文章里的链接零修改
- 不会因为后端服务名变化（比如 R2 改域名、VPS 换 IP）连带影响所有历史文章
- SEO 不会丢失（搜索引擎索引的是稳定 URL）
- **避免厂商锁定**——这是核心收益，跟时间无关

### 实施清单

- [x] CF 上添加 CNAME：`cdn.${DOMAIN} → ${VPS_IP}`（或 `${VPS_HOST}`），开橙云
- [x] VPS Caddy 加 server block：`cdn.${DOMAIN}`，`root /var/www/cdn`
- [x] 加 `Cache-Control: public, max-age=31536000, immutable` header

## 2. 路径结构：日期分桶

```
cdn.${DOMAIN}/YYYY/MM/文件名.ext

例：
cdn.${DOMAIN}/2026/05/iceland-aurora.jpg
cdn.${DOMAIN}/2026/05/test-101-climb.mp4
cdn.${DOMAIN}/2026/06/macbook-keyboard-step1.png
```

### 为什么按月分桶

- 5 年后翻文章一眼能定位"哪期资产"
- 单目录不会塞超过几百个文件，ls / rsync 都不卡
- 备份策略可以按月做增量：`~/blog-media/2026/05/` 整月归档

### 不要按文章 slug 分桶的理由

- 同一张图可能多篇文章引用（按 slug 会重复存）
- 文章 slug 改了图片路径要跟着改

## 3. 文件命名规范

```
✅ iceland-aurora-timelapse.mp4
✅ macbook-keyboard-cleaning-step1.jpg
✅ ai-thoughts-architecture-diagram.png

❌ IMG_1234.JPG                    （相机原始名，无信息）
❌ 冰岛极光.jpg                     （中文：URL encode 后丑、SEO 差）
❌ aaa.png / test.png / 123.jpg    （没意义）
❌ Screenshot 2026-05-06.png       （空格 + 大写 + 无描述）
```

### 规则细则

- 全小写
- 单词之间用 `-`（短横线），不用 `_` 或空格
- 必须描述性：看文件名能猜出内容
- 同主题多张加序号或修饰词：`-step1` `-step2` / `-before` `-after` / `-100crop`
- 扩展名小写：`.jpg` 不要 `.JPG`

### 为什么这些规则

- URL 友好：不需要 URL encode
- SEO 友好：搜索引擎从文件名提取语义
- grep 友好：找一张图直接 `grep iceland` 而不是回忆"是 IMG 几"
- 给未来的自己看的：5 年后只剩文件名能告诉你这是什么

### 资产不可变（append-only）铁律

**文件一旦上传，视为不可变。修改 = 新文件名，永远不要覆盖。**

```
✅ 重新 export 高清版    →  aurora.jpg + aurora-hires.jpg（共存）
✅ 修了构图              →  aurora.jpg + aurora-cropped.jpg
✅ 转了 webp 格式        →  aurora.jpg + aurora.webp（共存）

❌ 用同名新内容覆盖旧文件  →  CDN 缓存里还是旧内容，访客看到的最长 1 年都不变
```

#### 为什么不引入 hash 文件名

行业里另一种做法是给所有文件加内容 hash（如 `aurora.a3f9c2.jpg`），强行 cache bust。但对个人博客是反模式：

- 文件名失去 SEO 价值（搜索引擎从文件名抽语义）
- 两张图肉眼分不出哪是哪
- 命名规范文档要重写
- Hash 真正有价值的场景是构建产物（CSS/JS bundle），人手维护的内容资产不需要

不可变命名 + 描述性文件名是更自然的解：你本来就在"上传新图"的工作流里，不存在"覆盖旧图"的真实需求。

#### 与 `Cache-Control: immutable` 的内在一致性

§4 之后会看到我们给资源发 `Cache-Control: public, max-age=31536000, immutable`——这是**对浏览器和 CDN 的承诺**：这个 URL 的内容永不改变。

违反这个承诺，浏览器行为会不一致（有的严格遵守，有的偶尔 revalidate）。把"不可变"当成你接受的约束、而不是可选的策略，整个缓存链路才能稳定工作。

### 万一覆盖了：紧急 cache purge

如果某天破了规矩——覆盖了已上传文件、又忘了换名字——别等 1 年缓存自然过期，**用 CF API 手动清缓存**：

```bash
# 清单个 URL（最常用）
curl -X POST "https://api.cloudflare.com/client/v4/zones/${CF_ZONE_ID}/purge_cache" \
  -H "Authorization: Bearer $CF_PURGE_TOKEN" \
  -H "Content-Type: application/json" \
  --data '{"files":["https://cdn.${DOMAIN}/2026/05/aurora.jpg"]}'

# 清整个目录前缀（CF 不直接支持，要列出所有 URL，最多 30 个一批）

# 全站清（核选项，慎用——会让所有缓存重新回源，1-2 小时内 VPS 流量会陡增）
curl -X POST "https://api.cloudflare.com/client/v4/zones/${CF_ZONE_ID}/purge_cache" \
  -H "Authorization: Bearer $CF_PURGE_TOKEN" \
  -H "Content-Type: application/json" \
  --data '{"purge_everything":true}'
```

**需要单独的 token**：当前 VPS 上的 Caddy token 只有 `Zone:DNS:Edit` 权限，不够 purge。需要新签一个：

- 权限：`Zone:Cache Purge:Purge`
- Zone Resources：`${DOMAIN}`
- 不要保存到 VPS（这是临时使用的紧急 token）
- 用完即可 revoke

`$CF_PURGE_TOKEN` 在本地 shell 里 `export` 即可，不用进 .env（一次性使用，进了反而是风险）。

## 4. 存储分层：本地是源，VPS 是分发

```
~/blog-media/2026/05/iceland-aurora.jpg   ← 源（你的真相）
                ↓ rsync -avz
/var/www/cdn/2026/05/iceland-aurora.jpg   ← 分发副本（VPS）
                ↓ HTTP
Cloudflare 全球边缘节点缓存                 ← 给访客
```

### 三个目录的角色

| 角色 | 路径 | 备份责任 |
|---|---|---|
| 源 | `~/blog-media/`（本地 Mac） | iCloud / Time Machine / 你 |
| 分发 | `/var/www/cdn/`（VPS） | 视为可丢，rsync 重建 |
| 缓存 | CF 边缘节点 | CF 自己管，不可控 |

**核心铁律：本地必须先有，再传 VPS。永远不允许"先传 VPS 后才想起备份"。**

### 同步命令（写进 cheat sheet）

```bash
# 单向推送本地 → VPS（标准操作）
rsync -avz --progress ~/blog-media/ ${VPS_HOST}:/var/www/cdn/

# 验证（dry-run）
rsync -avzn ~/blog-media/ ${VPS_HOST}:/var/www/cdn/

# 反向兜底（如果本地丢了，从 VPS 拉回来）
rsync -avz ${VPS_HOST}:/var/www/cdn/ ~/blog-media/
```

## 5. 文章里的写法：直接写最终 URL

```markdown
✅ ![冰岛极光](https://cdn.${DOMAIN}/2026/05/iceland-aurora.jpg)
✅ <video src="https://cdn.${DOMAIN}/2026/05/climb.mp4" controls></video>

❌ ![冰岛极光](media:iceland-aurora-2026)        （别整占位符）
❌ ![冰岛极光]({{ media_url }}/aurora.jpg)        （别用模板变量）
```

### 为什么不用占位符 / 模板变量

- 占位符要求**构建期映射表**——多一层有状态的东西要维护，且要保证它和文章同步
- 出错面：映射表丢失 / 损坏 / 与实际不同步 → 全站图片 404
- 真要批量改，写个 30 行 Python 脚本扫所有 .md 替换即可，**无状态、跑完即弃**：

```python
# 假设将来要从 cdn.${DOMAIN} 迁到 media.${DOMAIN}
import re, pathlib
for md in pathlib.Path("./content").rglob("*.md"):
    text = md.read_text()
    new = re.sub(
        r"https://cdn\.wuyutaott\.com/",
        "https://media\.wuyutaott\.com/",
        text,
    )
    if new != text:
        md.write_text(new)
```

无状态的迁移脚本永远比有状态的映射系统更安全。

## 6. 上传流程：用 `mediactl` CLI

实际工具已实现：`scripts/mediactl`（Bash 脚本，约 200 行，**无状态**）。它把"重命名 + 压缩 + rsync + 验证 + 输出 markdown"压成一行命令。

### 6.1 一行加资产

```bash
./scripts/mediactl add ~/Downloads/IMG_4321.JPG --name iceland-aurora --compress
```

它内部按顺序做的事：

1. 校验 `--name` 符合命名规范（小写 + 短横线 + 数字）
2. 校验目标文件不存在（**资产不可变铁律**——已存在直接报错，不允许覆盖）
3. 复制到 `~/blog-media/<当前年>/<当前月>/<name>.<ext>`
4. （可选）`sips -Z 2000` 压缩到 2000px 宽
5. `rsync -az` 推到 `${VPS_HOST}:/var/www/cdn/`
6. `ssh chown caddy:caddy` 修正 VPS 权限
7. `curl -I` 验证 `https://cdn.${DOMAIN}/<相对路径>` 返回 200
8. 按文件类型生成 markdown 引用并**自动复制到剪贴板**

输出示例：
```
→ 复制到 ~/blog-media/2026/05/iceland-aurora.jpg
✓ 本地: ~/blog-media/2026/05/iceland-aurora.jpg (320K)
→ rsync 到 vps01-lax:/var/www/cdn/
✓ 已同步
→ 验证 https://cdn.wuyutaott.com/2026/05/iceland-aurora.jpg
✓ HTTP 200

Markdown 引用：
  <img src="https://cdn.wuyutaott.com/2026/05/iceland-aurora.jpg" width="800" />
✓ 已复制到剪贴板
```

文章里直接 cmd-V 粘贴引用即可。

### 6.2 所有子命令

| 命令 | 说明 |
|---|---|
| `mediactl add <file> [--name X] [--compress] [--no-rsync] [--year Y] [--month M]` | 加单个资产 |
| `mediactl sync` | 全量推：本地 → VPS（不带 --delete） |
| `mediactl preview` | sync 的 dry-run，预览会传什么 |
| `mediactl prune` | 带 `--delete` 的 sync，**会删 VPS 上本地没有的文件**，先 dry-run + 二次确认 |
| `mediactl ls [year/month]` | 列出本地资产库 |
| `mediactl url <year/month/file>` | 根据相对路径生成公网 URL，复制剪贴板 |
| `mediactl --help` | 完整用法 |

### 6.3 选项详解

```
--name <name>      目标文件名（不带扩展名）。不给的话用源文件名（会警告）
--compress         用 sips 压缩到 2000px 宽（仅 macOS）
--no-rsync         只复制本地，不上传 VPS（适合一次准备多张图、最后统一 sync）
--year YYYY        指定年（默认当前年，用于补传旧资产）
--month MM         指定月（同上）
```

### 6.4 视频和 GIF

- **视频**（`.mp4` `.webm` `.mov`）：`add` 子命令照常工作，输出的 markdown 是 `<video src="..." controls></video>`，需要的话手动改成无 controls + autoplay loop muted 形式（参考 §7）
- **GIF**：直接 `add` 即可，`--compress` 会被跳过（sips 不处理 GIF）

### 6.5 何时不该用 mediactl

- **批量补传一批历史资产**：直接 rsync 整个 `~/blog-media/` 更快
- **临时测试 / 一次性**：直接 scp 上去就行
- **要做特殊处理（视频转码、AV1 编码）**：mediactl 没集成，自己跑 ffmpeg + `mediactl add --no-rsync` + `mediactl sync`

### 6.6 手动工作流（mediactl 挂了 / 不可用时）

```bash
# 1. 准备文件
cp ~/Downloads/IMG_4321.JPG ~/blog-media/2026/05/iceland-aurora.jpg

# 2. （可选）压缩
sips -Z 2000 ~/blog-media/2026/05/iceland-aurora.jpg

# 3. 同步
source .env
rsync -avz ~/blog-media/ ${VPS_HOST}:/var/www/cdn/
ssh ${VPS_HOST} 'chown -R caddy:caddy /var/www/cdn'

# 4. 验证
curl -I https://cdn.${DOMAIN}/2026/05/iceland-aurora.jpg
```

mediactl 挂了不影响任何已上传资产——脚本是无状态的，`~/blog-media/` 和 VPS 上的文件该在还在。

## 7. 视频专项约定

参考 Weekly 的 4 种写法，按场景选：

### 7.1 小循环（< 10MB，当 GIF 用）
```html
<video width="600" preload muted autoplay loop playsinline>
  <source src="https://cdn.${DOMAIN}/2026/05/loop.mp4" type="video/mp4">
</video>
```

### 7.2 带声音 / 控制条
```html
<video width="800" preload controls>
  <source src="https://cdn.${DOMAIN}/2026/05/talk.mp4" type="video/mp4">
</video>
```

### 7.3 缩略图 + 点击全屏
```html
<a href="https://cdn.${DOMAIN}/2026/05/big.mp4" target="_blank">
  <video width="800" autoplay preload loop muted>
    <source src="https://cdn.${DOMAIN}/2026/05/big.mp4" type="video/mp4">
  </video>
</a>
```

### 7.4 大视频（> 200MB）走第三方
- 不要自己扛大视频，CF 免费版单文件 > 512MB 不缓存
- 用 B 站 / YouTube 链接：直接放 URL，不嵌 iframe

```markdown
<https://www.bilibili.com/video/BV1nYzDB3EKx>
```

## 8. 何时升级到下一级方案

**保持现规则不变**，除非满足以下任一条件：

| 触发条件 | 升级动作 |
|---|---|
| 资产数 > 1000 张 | 加一个 `media.yaml` manifest，记录元数据（alt、尺寸、备份位置） |
| 一年内迁移过 ≥ 2 次 | 同上，把 URL 抽到 manifest |
| 超过 3 个项目共用同一批资产 | 同上 + 抽离成独立子域 |
| 多人协作写博客 | 才考虑 DAM 平台（PicList / Immich / Cloudinary） |
| 视频总量 > 50GB | 视频迁 R2 或 bunny.net Stream，图片继续在 VPS |

升级触发条件未达成 = 规则继续跑。**不预先优化的根本理由不是"做不起"，而是更复杂的方案会引入更多失败模式**——架构级 over-engineering 的代价是结构性的，不会因为 AI 帮你写代码而消失。

| 验证命令 | `curl -I https://cdn.${DOMAIN}/<path>` |
